# FAST LANE — passer la détection de ~10 min à < 2 s

Date : 2026-09-28. Statut : **prototype construit et testé (17 tests verts), exécution live BLOQUÉE (clé Helius absente).**

## 1. Baseline mesurée — la latence actuelle, honnêtement

Pipeline actuel : PumpPortal WS → scan files → commit git → git fetch → cron track-unbiased.

| Étage | Mesure | Méthode |
|---|---|---|
| On-chain → `receivedAt` (scan file) | **non mesuré**, estimé à quelques secondes | WebSocket PumpPortal quasi-temps réel ; le vrai timestamp on-chain exigerait un accès RPC (indisponible) |
| `receivedAt` → commit data | **médiane ~5 min** (plage 0–10,4) | 20 derniers commits du scan-mirror : intervalle médian 10,4 min, p90 11,0, max 12,4 |
| Commit → ingestion track-unbiased | **médiane ~2–3 min** | End-to-end `receivedAt`→`discoveredAt` mesuré : **médiane 7,7 min** (n=304), p25 4,7, p75 12,0. Le p90 (68 min) est gonflé par le bootstrap initial — régime stable : 5–12 min |
| **Total on-chain → ingestion** | **~8–13 min typique** | Somme des étages |

Rappel du contexte : la migration arrive en **médiane 2,9 min** (vérifié sur données brutes, n=296 creates genuine le 27 sept.). Le pipeline actuel détecte donc le token typique **après** sa migration. Cible : < 2 s, soit un facteur ~400×.

## 2. Comparatif des options rapides

| Option | Latence attendue | Coût | Fiabilité | Verdict |
|---|---|---|---|---|
| **logsSubscribe standard (Helius WSS, plan gratuit)** | 0,5–2 s (benchmarks publics : pumpkit, Helius docs) | ~2 crédits / 0,1 Mo streamé ; volume du firehose **à mesurer en live** | Drops silencieux possibles → reconnexion avec backoff ; **pas de backfill** (limite documentée) | **RETENU pour le prototype** — plan gratuit, aucune infra entrante, 1 seule connexion WS sortante |
| Helius Enhanced WS (`transactionSubscribe`) | plus rapide (infra LaserStream) | 2–3 crédits / 0,1 Mo ; **plan Developer+/Business+ requis (payant)** | Idem + filtres avancés | Écarté pour le prototype (payant) ; option si le gratuit ne suffit pas |
| Helius webhooks | ~1–3 s | 1 crédit / événement livré | Retry ×3 ; **nécessite un endpoint HTTP public entrant** (infra à ouvrir sur la VM) | Écarté pour le prototype (infra entrante + même problème de filtrage) |
| Polling `getSignaturesForAddress` | latence de polling + firehose identique | 1 crédit / appel, mais polling permanent | Curseur fiable, mais lent et coûteux en continu | Écarté |
| Geyser gRPC | 50–500 ms | $200–2 000/mois | Excellente | Overkill pour de la détection |
| **Helius Parsed Streams** (nouveau, 1 crédit/événement) | ~0,5–2 s | **~21 000 crédits/mois** si filtrable par type d'événement (= nb de creates/jour) | À évaluer | **À VÉRIFIER** — si le filtrage par événement Create existe, c'est l'option idéale. Non confirmé dans la doc publique consultée |

**Point de design clé** : avec `logsSubscribe`, on ne reçoit que signature + logs (pas les clés de compte). Le prototype parse donc le **mint directement depuis l'événement Anchor `Create`** (`Program data:` → Borsh : name, symbol, uri, mint, bondingCurve, user) — **zéro appel RPC supplémentaire**. Sans ça, il faudrait un `getTransaction` par create (~21 000/jour = 630 000 crédits/mois, la moitié du plan gratuit).

**Contrainte respectée** : aucune connexion WebSocket vers PumpPortal (la règle « une seule connexion » anti-bannissement reste au collecteur principal).

## 3. Prototype construit

- `lab/collect/fastlane.ts` — détecteur : `logsSubscribe` (`mentions: [programme Pump.fun]`, commitment `processed`), `slotSubscribe` pour l'horloge, parsing Borsh pur et testable, `SlotClock` (interpolation des slots, estimation **avant** ancrage pour éviter l'auto-référence), reconnexion backoff exponentiel, ping 30 s, stats (notifications, creates, latence p50/p95/p99, reconnects).
- `lab/collect/fastlane-prototype.ts` — CLI : `--duration-min` (défaut 45), écrit `data/fastlane/fastlane-<date>.jsonl` + résumé stats. **Refuse de tourner sans `HELIUS_API_KEY`** (exit 3, message explicite). Observation pure : aucune transaction, aucun ordre.
- `tests/fastlane.test.ts` — **17 tests verts** : parsing Borsh (valide, base64 invalide, tronqué, longueurs absurdes), détection/rejet dans les logs, `SlotClock` (interpolation, extrapolation, régression), détecteur avec WebSocket simulé (latence mesurée à 800 ms comme attendu, reconnexion).

Validation : `tsc` propre sur les nouveaux fichiers (les 32 erreurs pré-existantes de `lab/backtest/` sont inchangées) ; suite complète 526 verts + 1 échec attendu. Note : `tests/signals.test.ts` échoue actuellement à cause de **modifications non commitées d'un agent parallèle** sur `lab/signals/earlybuyers.ts` — hors scope, signalé au parent.

## 4. Exécution live — BLOQUÉE

`HELIUS_API_KEY` est absente de l'environnement du sous-agent (vérifié : env, fichiers du workspace, cron.d — seules des références en documentation). Conformément à la consigne, **aucune clé inventée, aucune mesure simulée** : le prototype s'arrête avec un message clair.

**Pour lancer l'observation réelle** (45–60 min recommandées) :
```bash
export HELIUS_API_KEY=<clé>   # jamais en clair dans le chat
npx tsx lab/collect/fastlane-prototype.ts --duration-min 60
```

**Deux inconnues que seul le run live tranchera** :
1. **Le volume du firehose** (toutes les txs du programme Pump.fun, pas seulement les creates) — c'est lui qui détermine le coût réel du streaming. Le run de 60 min le mesure empiriquement de façon bornée (quelques milliers de crédits).
2. **L'accès réseau sortant** : le garde-fou local (sentinel) a bloqué mes sondes HTTPS vers Helius cette nuit. Si `wss://mainnet.helius-rpc.com` est également bloqué depuis cet environnement, le run devra se faire là où l'egress est autorisé.

Le programme ID Pump.fun (`6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`) vient de la connaissance publique ; le prototype loggue les échecs de parse, donc un mauvais programme se verrait immédiatement (zéro create détecté).

## 5. Modèle de coût mensuel (estimation, à calibrer en live)

Hypothèses mesurées : **21 397 creates/jour** (27 sept., scan files) ; notification WS ~300–500 octets.

| Scénario firehose | Volume/jour | Crédits/mois (2 / 0,1 Mo) | Dans 1 M gratuit ? |
|---|---|---|---|
| 1 M notifications/jour | 400 Mo | ~240 000 | ✅ Oui |
| 5 M notifications/jour | 2 Go | ~1 200 000 | ❌ Non → plan payant ou Parsed Streams |
| 10 M notifications/jour | 4 Go | ~2 400 000 | ❌ Non |

Le repo consomme actuellement 17 731 crédits/mois : la marge est confortable **si** le firehose reste sous ~3 M notifications/jour. Le run d'observation répondra avec un chiffre, pas une hypothèse.

## 6. Recommandation

1. **Le design est viable et peu coûteux à valider** : un run d'une heure coûte quelques milliers de crédits et répond aux deux inconnues (latence réelle, volume du firehose).
2. **Lancer le run live** dès que la clé est disponible dans un environnement à egress autorisé.
3. Si le firehose dépasse le budget gratuit : vérifier le filtrage par événement de **Parsed Streams** (1 crédit/création ≈ 21 000/mois, idéal) avant d'envisager un plan payant.
4. **Ne jamais ouvrir un second WebSocket PumpPortal** — le bannissement d'une heure tuerait le collecteur principal.
5. Rappel honnête : < 2 s de détection, c'est le **ticket d'entrée**, pas l'edge. La sélection dans la fenêtre de 3 minutes reste le vrai problème — la batterie pré-enregistrée (T-SERIAL-HOT et al.) dira si le signal wallet survit aux données propres.
